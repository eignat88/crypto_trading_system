# План загрузки данных в PostgreSQL

**Проект:** Crypto Trading System
**Обновлено:** 20.08.2026
**Статус документа:** кодовый foundation готов; требуется пилот на целевой БД
**Контур первой версии:** Bybit Spot, `BTCUSDT` и `ETHUSDT`

---

## 1. Цель

Организовать надёжную, повторяемую и контролируемую загрузку рыночных данных из Bybit в PostgreSQL по цепочке:

```text
Bybit API
    → RAW: исходные данные и журнал запросов
        → DDS: проверенные нормализованные данные
            → Indicators / Market Regime
                → MART: отчётность и метрики
```

Первая задача — создать достоверную базу исторических свечей для backtest и последующего paper trading. Торговые операции не являются частью процесса загрузки данных и должны оставаться выключенными.

---

## 2. Основные принципы

1. Сначала данные сохраняются в RAW, затем преобразуются в DDS.
2. RAW хранит данные максимально близко к ответу API и не используется стратегиями напрямую.
3. Повторный запуск не должен создавать дубли.
4. Каждая успешно зафиксированная порция данных должна иметь checkpoint.
5. Checkpoint обновляется только в одной транзакции с записью данных.
6. Пропуски, дубли и некорректные значения должны обнаруживаться до расчёта индикаторов.
7. В DDS загружаются только закрытые и валидные свечи.
8. Время хранится в `timestamptz` и UTC.
9. Цены и объёмы хранятся как `numeric`, без использования `float` для денежных значений.
10. Массовые `UPDATE` в RAW не применяются. Исправление логики выполняется в коллекторе или при переносе `RAW → DDS`.
11. Сбой одного потока `symbol + interval` не должен требовать повторной загрузки всей истории.
12. До завершения проверки качества данные не допускаются к backtest, paper trading или live trading.

### Исправление блокера `close_time`

`BybitClient.get_candles()` вычисляет `close_time` как `open_time + interval_duration`.
Единый справочник длительностей используется клиентом Bybit и коллектором. Функция
`dds.load_raw_candles()` переносит в DDS только строки, у которых:

```sql
close_time IS NOT NULL
AND close_time <= p_as_of
```

Следствие: текущая незакрытая свеча сохраняется в RAW, но до наступления `close_time`
увеличивает `deferred_count` и не создаёт запись в `dds.candle`.

Выполнено:

1. вычисление `close_time` для `5m`, `15m`, `1h`, `4h`, `1d`;
2. unit-тесты всех поддерживаемых интервалов;
3. сквозной unit-тест фиксированного ответа `API → RAW` и проверка границы DDS;
4. проверка SQL-контракта отбора только закрытых свечей.

До массовой загрузки остаётся выполнить пилот на тестовой PostgreSQL 17 и подтвердить
фактические значения `inserted_count`, `deferred_count` и отсутствие дублей.

**Статус:** исправлено в коде и unit-тестах; требуется интеграционная проверка на PostgreSQL.

## 5. Модель хранения

## 5.1. RAW

### `raw_market.candles`

Назначение — хранение свечей максимально близко к ответу Bybit.

Ключ защиты от дублей:

```text
exchange_name + symbol + interval_code + open_time
```

Основные поля:

- идентификаторы биржи, инструмента и интервала;
- `open_time`, `close_time`;
- OHLCV;
- quote volume и количество сделок, если источник их предоставляет;
- `source_payload` — исходная строка ответа API;
- `loaded_at` — время фиксации в PostgreSQL.

Запись выполняется через:

```sql
ON CONFLICT (exchange_name, symbol, interval_code, open_time)
DO NOTHING
```

Это обеспечивает безопасный повторный запуск, но не обновляет уже сохранённую текущую свечу. Поэтому исторический коллектор должен загружать только завершённые свечи либо иметь отдельную контролируемую логику обновления последней незакрытой свечи.

### `raw_system.api_responses`

Назначение — аудит обращений к API:

- endpoint;
- request ID;
- время запроса и ответа;
- HTTP status;
- параметры запроса;
- полный ответ;
- текст ошибки.

### `raw_system.loading_journal`

Назначение — журнал успешно обработанных диапазонов и checkpoint для продолжения загрузки:

- поток `exchange + symbol + interval`;
- начальное и конечное время порции;
- количество вставленных строк;
- статус;
- ошибка;
- время начала и завершения.

## 5.2. DDS

### `dds.instrument`

Справочник поддерживаемых инструментов. Для MVP заранее добавляются:

- Bybit / BTCUSDT / BTC / USDT;
- Bybit / ETHUSDT / ETH / USDT.

### `dds.candle`

Содержит только закрытые, нормализованные и прошедшие проверки свечи.

Уникальность:

```text
instrument_id + interval_code + open_time
```

### `dds.data_quality_event`

Карантин ошибок качества. Невалидная строка не попадает в `dds.candle`, но ошибка сохраняется с исходным payload и счётчиком повторных обнаружений.

### `dds.etl_checkpoint`

Хранит watermark отдельно для каждого потока:

```text
exchange_name + symbol + interval_code
```

### `dds.etl_run`

Хранит результат каждого запуска:

- `source_count`;
- `inserted_count`;
- `rejected_count`;
- `deferred_count`;
- статус и текст ошибки;
- время начала и завершения.

## 5.3. MART

MART не должен заполняться напрямую из RAW. Источником служат только проверенные данные DDS.

Реализованный `scripts/load_mart.py` запускает идемпотентную загрузку `DDS → MART`.
В production она должна выполняться после завершения:

1. исторической загрузки свечей;
2. проверки целостности DDS;
3. расчёта индикаторов и режима рынка;
4. разработки отдельных идемпотентных агрегатов.

## Этап 5. Пилотный перенос RAW → DDS

Запуск для одного потока:

```powershell
python .\scripts\load_dds.py `
    --exchange bybit `
    --symbol BTCUSDT `
    --interval 1h
```

Ожидаемый формат результата:

```text
run=<id> bybit BTCUSDT 1h: source=<N> inserted=<N> rejected=0 deferred=<0 или 1>
```

Повторный запуск должен завершиться без дублей. Для неизменившегося источника ожидается `inserted=0`.

### Проверка DDS

```sql
SELECT
    i.exchange_name,
    i.symbol,
    c.interval_code,
    count(*) AS rows_count,
    min(c.open_time) AS min_open_time,
    max(c.open_time) AS max_open_time
FROM dds.candle c
JOIN dds.instrument i ON i.instrument_id = c.instrument_id
GROUP BY i.exchange_name, i.symbol, c.interval_code
ORDER BY i.exchange_name, i.symbol, c.interval_code;
```

Последние запуски ETL:

```sql
SELECT
    run_id,
    exchange_name,
    symbol,
    interval_code,
    source_count,
    inserted_count,
    rejected_count,
    deferred_count,
    status,
    error_message,
    started_at,
    completed_at
FROM dds.etl_run
ORDER BY run_id DESC
LIMIT 20;
```

Ошибки качества:

```sql
SELECT
    exchange_name,
    symbol,
    interval_code,
    check_name,
    count(*) AS affected_candles,
    sum(occurrence_count) AS occurrences
FROM dds.data_quality_event
GROUP BY exchange_name, symbol, interval_code, check_name
ORDER BY affected_candles DESC;
```

### Критерий готовности

- закрытые валидные свечи загружены в DDS;
- открытая свеча отложена;
- невалидные строки записаны в `dds.data_quality_event`;
- повторный запуск не создаёт дублей;
- checkpoint обновлён только после успешной транзакции.

## Этап 6. Полная историческая загрузка

После успешного пилота выполнить загрузку по одному потоку за раз. Рекомендуемый порядок:

1. `BTCUSDT 1d`;
2. `ETHUSDT 1d`;
3. `BTCUSDT 4h`, затем `ETHUSDT 4h`;
4. `1h`;
5. `15m`;
6. `5m`.

Такой порядок позволяет сначала проверить короткие наборы и быстрее обнаружить ошибки модели данных.

Пример полной RAW-загрузки:

```powershell
python .\scripts\load_history.py `
    --symbol BTCUSDT ETHUSDT `
    --interval 5m 15m 1h 4h 1d `
    --years 3 `
    --resume
```

После каждого потока запускается `RAW → DDS` и выполняется сверка количества строк.

### Правило при сбое

Не запускать полную загрузку заново, пока не проверено:

- какие транзакции уже зафиксированы;
- последний успешный checkpoint;
- наличие строк в RAW;
- наличие строк в DDS;
- причина остановки;
- можно ли безопасно продолжить с `--resume`.

## Этап 7. Контроль полноты временного ряда

Проверка пропусков должна выполняться отдельно для каждого `symbol + interval`.

Пример для часовых свечей:

```sql
WITH ordered AS (
    SELECT
        i.symbol,
        c.interval_code,
        c.open_time,
        lag(c.open_time) OVER (
            PARTITION BY i.symbol, c.interval_code
            ORDER BY c.open_time
        ) AS previous_open_time
    FROM dds.candle c
    JOIN dds.instrument i ON i.instrument_id = c.instrument_id
    WHERE i.exchange_name = 'bybit'
      AND c.interval_code = '1h'
)
SELECT
    symbol,
    interval_code,
    previous_open_time,
    open_time,
    open_time - previous_open_time AS gap
FROM ordered
WHERE previous_open_time IS NOT NULL
  AND open_time - previous_open_time <> interval '1 hour'
ORDER BY symbol, open_time;
```

Для остальных интервалов ожидаемый шаг должен задаваться явно. Обнаруженный пропуск не заполняется синтетической свечой без отдельного обоснованного решения.

### Критерий готовности

- необъяснённых пропусков нет;
- временной ряд строго возрастает;
- свечи выровнены по границам интервалов;
- диапазон RAW соответствует диапазону DDS за исключением открытых и отклонённых свечей.

## Этап 8. Автоматический инкрементальный процесс

После исторической загрузки необходимо создать планировщик, который выполняет:

1. запрос последних закрытых свечей;
2. сохранение ответа и свечей в RAW;
3. фиксацию checkpoint;
4. запуск `RAW → DDS`;
5. проверки качества;
6. расчёт индикаторов;
7. определение режима рынка;
8. запись метрик и результата запуска;
9. уведомление при ошибке.

Процесс должен запускаться после завершения интервала с небольшим техническим запасом. Для MVP допустим последовательный запуск без параллельной обработки одного и того же потока.

### Критерий готовности

- один интервал не обрабатывается дважды;
- пропущенный запуск восстанавливается по checkpoint;
- незакрытая свеча не используется стратегией;
- ошибка PostgreSQL или API блокирует дальнейшую обработку данного цикла;
- состояние после перезапуска восстанавливается.

---

## 7. Транзакционность и идемпотентность

### API → RAW

В одной транзакции должны фиксироваться:

- строки свечей;
- информация об API-ответе;
- запись успешного диапазона в `loading_journal`.

Если транзакция откатывается, checkpoint не должен продвигаться.

### RAW → DDS

Для каждого потока функция:

1. блокирует строку checkpoint через `FOR UPDATE`;
2. определяет верхнюю границу `loaded_at`;
3. формирует набор кандидатов;
4. отправляет ошибки в карантин;
5. вставляет валидные свечи с `ON CONFLICT DO NOTHING`;
6. обновляет checkpoint;
7. фиксирует результат в `etl_run`.

Одновременный запуск двух обработчиков одного потока запрещён логикой блокировки checkpoint.

---

## 8. Контроль качества данных

Обязательные проверки до допуска свечи в DDS:

| Проверка | Условие |
|---|---|
| Время закрытия | `close_time IS NOT NULL` и `close_time > open_time` |
| Закрытая свеча | `close_time <= as_of` |
| Положительные цены | OHLC > 0 |
| Верхняя граница | `high >= open`, `high >= close` |
| Нижняя граница | `low <= open`, `low <= close` |
| Диапазон | `high >= low` |
| Объём | `volume >= 0` |
| Дополнительная активность | `quote_volume >= 0`, `trade_count >= 0` при наличии |
| Уникальность | одна свеча на ключ потока и `open_time` |
| Последовательность | шаг между свечами соответствует интервалу |
| UTC | timestamps содержат timezone |

Необходимо также добавить сверку:

```text
закрытые RAW-кандидаты
= вставленные DDS
+ отклонённые строки
+ уже существующие валидные DDS-строки
```

## 9. Мониторинг загрузки

Для каждого запуска необходимо контролировать:

- начало и завершение;
- источник, символ и интервал;
- диапазон времени;
- количество полученных, вставленных, отклонённых и отложенных строк;
- длительность;
- скорость строк/сек;
- количество повторных попыток API;
- HTTP 429 и другие ошибки Bybit;
- ошибки PostgreSQL;
- возраст последней закрытой свечи;
- размер RAW и DDS;
- рост WAL при больших операциях;
- зависшие транзакции;
- состояние checkpoint.

Минимальные аварийные условия:

- отсутствует ожидаемая свеча;
- `rejected_count > 0`;
- `deferred_count` больше ожидаемого числа текущих свечей;
- checkpoint не продвигается;
- API возвращает пустой пакет внутри ожидаемого диапазона;
- расхождение количества RAW и DDS не объясняется карантином;
- PostgreSQL недоступен.

При аварийном условии новые торговые сигналы для затронутого потока должны быть запрещены до восстановления данных.

## 10. Обработка ошибок

| Ошибка | Безопасное действие |
|---|---|
| Timeout или сетевая ошибка GET | Повторить публичный запрос с ограниченным backoff |
| HTTP 429 | Уменьшить частоту, повторить после задержки |
| Ошибка авторизации | Остановить процесс, проверить локальную конфигурацию |
| Пустой пакет внутри диапазона | Остановить поток и зафиксировать разрыв, не перескакивать checkpoint |
| Дубли в ответе | Остановить порцию, записать ошибку |
| Пропуск между свечами | Остановить порцию, повторно запросить диапазон |
| Ошибка INSERT | Откатить транзакцию, checkpoint не обновлять |
| Невалидная свеча | Сохранить RAW, записать событие качества, не переносить в DDS |
| Неизвестное состояние загрузки | Проверить RAW, DDS и журналы до повторного запуска |
| Недоступна БД | Остановить цикл; торговлю не выполнять |
