Проанализированная ветка: `main`

## 1. Вывод

Проект имеет хорошую заготовку архитектуры: выделены модули биржи, сбора данных,
индикаторов, стратегии, Risk Engine и backtest; созданы схемы RAW, DDS и MART;
присутствуют unit-тесты.

Но текущий статус следует считать **«прототип, не готовый к paper trading»**.
Перед развитием новых стратегий необходимо исправить критические ошибки:

1. исторические свечи Bybit обрабатываются в неверном порядке;
2. авторизация приватных Bybit-запросов реализована не по формату V5;
3. торговый POST-запрос может быть автоматически отправлен повторно;
4. отсутствует рабочий процесс `RAW → DDS`;
5. расчёт стоимости портфеля в backtest неверен;
6. Trend DCA фактически не интегрирована с Backtest Engine и Risk Engine;
7. состояние Risk Engine, стратегии и emergency stop не сохраняется;
8. текущие тесты не обнаруживают основные архитектурные ошибки;
9. GitHub Actions/CI отсутствует;
10. диагностические отчёты PostgreSQL попали в публичный репозиторий.

До исправления пунктов 1–8 нельзя переходить к paper trading, а тем более к live.

## 3. Критические дефекты

### P0. Загрузка свечей Bybit

Bybit возвращает kline в обратном порядке `startTime`, а коллектор продолжает
загрузку от `candles[-1]`. Это может приводить к неправильному checkpoint,
повторной загрузке одного диапазона или преждевременному завершению.

Исправление:

- сортировать ответ по `open_time ASC`;
- двигать границу только по `max(open_time)`;
- рассчитывать следующий интервал через длительность таймфрейма, а не `+1 секунда`;
- проверять монотонность, дубли и пропуски;
- сохранять исходный JSON, request ID и время запроса;
- checkpoint фиксировать в одной транзакции с загруженным batch.

### P0. Приватные запросы и повторная отправка ордеров

Подпись Bybit V5 должна учитывать `recv_window`, а POST должен подписывать
JSON body. Сейчас параметры POST отправляются как query string, а общий retry
повторяет любой запрос, включая `POST /v5/order/create`.

Исправление:

- разделить публичные GET, приватные GET и торговые POST;
- реализовать подпись V5 по официальной спецификации;
- запретить автоматический retry торгового POST после неопределённого результата;
- до возможного повтора запросить состояние по уникальному `client_order_id`;
- сделать `client_order_id` обязательным для любого ордера;
- добавить отдельные исключения: timeout, auth, rate limit, API reject,
  unknown order state;
- API-ключ live должен быть без права вывода.

### P0. Ошибочная стоимость портфеля в backtest

После покупки из cash вычитается полная стоимость позиции, но `total_equity`
прибавляет только нереализованный PnL, а не текущую рыночную стоимость позиции.
Из-за этого equity и drawdown считаются неверно.

Дополнительно:

- повторное открытие по одному символу перезаписывает позицию;
- DCA не объединяет количество и среднюю цену;
- `stop_loss` и `take_profit` сигнала теряются при исполнении;
- short присутствует, хотя проект ограничен spot;
- сигнал стратегии является dataclass, а Backtest Engine ожидает dict;
- Risk Engine не участвует в обработке сигнала;
- trailing stop в стратегии вычисляется от текущей цены и фактически не срабатывает.

### P0. Отсутствует рабочий `RAW → DDS`

Созданы таблицы DDS, но нет ETL-сервиса или SQL-процедуры, которая:

- создаёт инструменты BTCUSDT и ETHUSDT;
- переносит свечи из RAW идемпотентно;
- отделяет закрытые свечи от незакрытой текущей свечи;
- проверяет качество;
- ведёт checkpoint и журнал;
- формирует отчёт о количестве source/inserted/rejected.

Ограничение `CHECK` в `dds.candle` не позволяет вставить плохую свечу, тогда как
`DataQualityChecker` предполагает наличие плохой свечи в DDS и пытается пометить
её `is_valid=false`. Нужно выбрать одну непротиворечивую модель:

- рекомендуется отклонять плохие строки при ETL и сохранять их в
  `dds.data_quality_event`, а в `dds.candle` хранить только валидные свечи.

### P1. Risk Engine

Не используются или не проверяются:

- `max_risk_per_trade`;
- доступный баланс;
- доступность PostgreSQL и API;
- результат reconciliation;
- неизвестный статус ордера;
- направление сделки: продажа/сокращение позиции ошибочно может считаться
  увеличением exposure;
- сохранение risk events и состояния emergency stop.

### P1. Репозиторий и CI

- Нет GitHub Actions и обязательных checks.
- `STATUS.md` и `ROADMAP.md` не отражают уже добавленные DDS/MART/коллектор.
- В публичный репозиторий добавлены `monitoring/diagnostic_reports/*` с данными
  локального компьютера и структуры PostgreSQL.
- В `.gitignore` нет исключения для diagnostic reports.

## 4. Новый порядок развития

### Этап 0. Зафиксировать безопасную базу — 1–2 дня

Задачи:

1. Добавить GitHub Actions: `ruff`, `mypy`, `pytest`, coverage.
2. Удалить diagnostic reports из текущей версии репозитория и добавить
   `monitoring/diagnostic_reports/` в `.gitignore`.
3. Проверить историю на API keys, DB passwords и другие секреты.
4. Обновить `STATUS.md` по фактическому состоянию.
5. Зафиксировать Python 3.11 и воспроизводимую установку зависимостей.

Критерий готовности:

- чистая установка проекта проходит;
- все текущие тесты запускаются в CI;
- секретов и локальных отчётов в актуальной ветке нет.

### Этап 1. Исправить Exchange Client и загрузку RAW — 3–5 дней

Задачи:

1. Исправить сортировку и пагинацию свечей.
2. Добавить interval-aware переход к следующей свече.
3. Добавить timeout/retry только для безопасных публичных запросов.
4. Сохранять `source_payload`, request ID и время загрузки.
5. Исправить атомарный checkpoint.
6. Добавить контроль пропусков и повторный добор только конкретных интервалов.
7. Исправить V5 authentication, но пока не активировать торговые методы.

Тесты:

- reversed API response;
- пустая страница;
- overlapping pages;
- дубли;
- сетевой timeout;
- HTTP 429;
- разрыв внутри истории;
- перезапуск с checkpoint.

Критерий готовности:

- BTCUSDT и ETHUSDT загружаются повторно без дублей;
- интервалы непрерывны;
- повторный запуск не начинает загрузку заново;
- проверка приватного read-only endpoint проходит отдельно.

### Этап 2. Реализовать `RAW → DDS` и качество данных — 3–5 дней

Задачи:

1. Создать `dds.data_quality_event`.
2. Реализовать идемпотентный batch ETL.
3. Добавить checkpoint `raw_to_dds`.
4. Обрабатывать только закрытые свечи.
5. Проверять OHLCV, UTC, уникальность и непрерывность.
6. Сделать reconciliation количества RAW/DDS/rejected.
7. Добавить CLI-команду запуска ETL.

Критерий готовности:

- для каждой валидной закрытой RAW-свечи существует ровно одна DDS-свеча;
- плохие строки не попадают в `dds.candle`;
- причина каждого отклонения сохранена;
- повторный ETL идемпотентен.

### Этап 3. Исправить индикаторы и Market Regime — 2–4 дня

Задачи:

1. Сделать расчёт инкрементальным с warm-up окном 200+ свечей.
2. Не пересчитывать всю историю на каждом запуске.
3. Сохранить версию алгоритма и параметры.
4. Запретить использование будущих свечей.
5. Добавить тесты против эталонных значений EMA, RSI и ATR.
6. Добавить проверку, что сигнал на времени `T` использует данные не позже `T`.

Критерий готовности:

- полный и инкрементальный расчёт дают одинаковый результат;
- повторный запуск не создаёт дублей;
- параметры и версия воспроизводимы.

### Этап 4. Переписать ядро Backtest Engine — 5–8 дней

Правильная цепочка:

`Candle → Indicators → Regime → Strategy Signal → Risk Engine → Fill Model → Portfolio`

Задачи:

1. Ввести единые типизированные модели `Signal`, `RiskDecision`, `Order`,
   `Fill`, `Position`.
2. Удалить поддержку short из MVP.
3. Исправить cash, market value, equity и drawdown.
4. Реализовать увеличение spot-позиции с пересчётом средней цены.
5. Передавать stop-loss/take-profit в позицию.
6. Реализовать trailing high-water mark.
7. Подключить Risk Engine к каждому сигналу.
8. Учитывать maker/taker, slippage, latency, partial fill и незакрытую позицию.
9. Сохранять параметры запуска, сигналы, risk decisions, orders, fills и метрики.
10. Добавить Buy & Hold и обычный DCA как benchmarks.

Критерий готовности:

- `equity = cash + market value` для spot;
- сохранение стоимости выполняется на покупке без комиссии;
- комиссии и slippage уменьшают результат;
- каждый сигнал имеет решение Risk Engine;
- одинаковый seed и входные данные дают одинаковый результат;
- отсутствует look-ahead bias.

### Этап 5. Довести Trend DCA и Risk Engine — 3–5 дней

Задачи:

1. Привести DCA-доли к общему лимиту позиции 10%.
2. Определить размеры base и safety orders как доли от лимита позиции, а не от
   всего капитала.
3. Добавить ATR-based stop или явно зафиксировать иной способ расчёта риска.
4. Реализовать все коды отказа Risk Engine.
5. Разделить открытие, увеличение и сокращение позиции.
6. Сохранять risk events.
7. Сделать emergency stop персистентным и fail-closed.

Критерий готовности:

- стратегия не может обойти Risk Engine;
- позиция по активу и общая загрузка никогда не превышают лимиты;
- после перезапуска emergency stop остаётся активным;
- продажа для закрытия позиции разрешается безопасно даже при запрете новых входов.

### Этап 6. Backtest и walk-forward — 1–2 недели

Задачи:

1. Период: не менее одного полного рыночного цикла, если данные доступны.
2. Разделение 12 месяцев train / 3 месяца test со скользящим окном.
3. BTCUSDT и ETHUSDT считать раздельно и совместно.
4. Сравнить Trend DCA с Buy & Hold и обычным DCA.
5. Сохранять Net Profit, Max Drawdown, Sharpe, Profit Factor, комиссии,
   slippage, exposure и число сделок.
6. Не добавлять Grid, пока Trend DCA не завершила полный цикл оценки.

Критерий готовности:

- положительный результат после комиссий не только на train;
- max drawdown не выше 10%;
- параметры устойчивы на соседних окнах;
- результат не зависит от одной короткой фазы рынка.

### Этап 7. Paper Exchange и восстановление — 2–3 недели

Задачи:

1. Реализовать `TRADING_MODE=paper`; неизвестное значение должно завершать
   запуск без торговли.
2. Виртуальные balances, orders, fills и positions хранить в DDS.
3. Реализовать частичное исполнение и жизненный цикл ордера.
4. После рестарта восстанавливать позиции, ордера, стратегию, Risk Engine и
   последний интервал.
5. Добавить failure-тесты: сеть, API, PostgreSQL, kill/restart.
6. Реализовать ежедневный отчёт и алерты.

Критерий готовности:

- рестарт не меняет состояние;
- один интервал не обрабатывается дважды;
- неизвестный ордер блокирует новые сделки;
- все действия доступны для аудита.

### Этап 8. Paper trading — минимум 90 дней

Условия:

- минимум 90 дней непрерывной работы;
- минимум 100 закрытых сделок;
- нет критических ошибок и расхождений;
- положительный результат после комиссий;
- drawdown не выше 10%;
- emergency stop и recovery проверены.

До выполнения условий live запрещён.

### Этап 9. Live и reconciliation

Только после paper:

1. Реализовать отдельный Execution Engine.
2. Ввести обязательный уникальный `client_order_id`.
3. После timeout сначала проверять состояние ордера, а не повторять POST.
4. Реализовать reconciliation balances/orders/fills/positions.
5. При расхождении блокировать новые ордера и включать emergency stop.
6. Пилот: не более 500 USDT, spot, без плеча.

## 5. Ближайший спринт

Рекомендуемый первый спринт:

1. CI и очистка репозитория.
2. Исправление Bybit kline pagination.
3. Тесты пагинации и checkpoint.
4. Исправление V5 signature.
5. Запрет retry для `place_order`.
6. Реализация минимального `RAW → DDS`.
7. Reconciliation RAW/DDS.

Результат спринта:

- надёжная и воспроизводимая база рыночных данных;
- торговые методы остаются выключенными;
- можно безопасно переходить к исправлению backtest.

## 6. Что пока не делать

- не добавлять Grid;
- не подключать 3Commas;
- не делать live trading;
- не добавлять фьючерсы, margin, leverage или short;
- не оптимизировать параметры стратегии;
- не увеличивать капитал;
- не строить сложный UI;
- не подключать ML.

Приоритет проекта: сохранность капитала → корректность данных и исполнения →
воспроизводимость backtest → доходность → скорость разработки.
