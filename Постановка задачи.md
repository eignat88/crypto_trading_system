# Постановка задачи
## Интеграция NautilusTrader в проект `crypto_trading_system` и подключение Bybit Spot
## проект NautilusTrader в папке D:\py_pro\nautilus_trader-develop

### 1. Цель задачи

Перевести проект `crypto_trading_system` на архитектуру, в которой **NautilusTrader используется как основной trading engine и адаптер взаимодействия с Bybit**, сохранив собственные модули проекта для хранения данных, индикаторов, стратегий, Risk Engine, мониторинга и отчётности.

На первом этапе необходимо реализовать минимальный рабочий контур:

**Bybit Public API → NautilusTrader → BTCUSDT/ETHUSDT Spot → приложение → PostgreSQL**

Реальную торговлю на данном этапе **не подключать**.

---

# 2. Основные ограничения проекта

Обязательные ограничения:

- биржа: Bybit;
- только Spot;
- инструменты:
  - `BTCUSDT`;
  - `ETHUSDT`;
- без фьючерсов;
- без perpetual;
- без маржинальной торговли;
- без кредитного плеча;
- без short;
- без мартингейла;
- без ML;
- без 3Commas;
- реальные ордера на данном этапе запрещены;
- API Secret для получения публичных рыночных данных не требуется;
- все timestamps хранить в UTC;
- денежные значения в Python рассчитывать через `Decimal`;
- конфигурацию не хранить непосредственно в Python-коде;
- приложение должно поддерживать повторный безопасный запуск.

# 3. Роль NautilusTrader

NautilusTrader использовать для:

- подключения к Bybit;
- REST/WebSocket взаимодействия;
- получения market data;
- определения инструментов;
- дальнейшего backtesting;
- дальнейшего paper/live execution;
- обработки событий ордеров;
- fills;
- reconciliation.

Необходимо избегать дублирования функциональности NautilusTrader собственным кодом без необходимости.

Собственный проект должен отвечать за:

- RAW;
- DDS;
- MART;
- конфигурацию;
- Indicators;
- Market Regime;
- Strategies;
- Risk Engine;
- Monitoring;
- Reporting;
- Emergency Stop;
- дополнительные бизнес-ограничения.


# 7. Trading Mode

Режим работы должен задаваться исключительно через:

```text
TRADING_MODE
```

Допустимые значения на текущем этапе:

```text
paper
```

В будущем:

```text
paper
live
```

До реализации live:

```text
TRADING_MODE=live
```

должен приводить к безопасному отказу запуска execution.

При:

```text
TRADING_MODE=<неизвестное значение>
```

также запрещать execution.

Fail-safe поведение:

```text
неизвестная конфигурация
        ↓
торговля запрещена
```

# 11. RAW

RAW должен хранить данные максимально близко к ответу источника.

Минимальная таблица:

```text
raw_bybit.market_data
```

или более специализированные таблицы:

```text
raw_bybit.trades
raw_bybit.bars
raw_bybit.quotes
```

На первом этапе достаточно реализовать хранение bars.

Пример логической структуры:

```sql
raw_bybit.bars
```

Поля минимум:

```text
id
instrument_id
bar_type
ts_event
ts_init
open
high
low
close
volume
raw_payload
request_id
loaded_at
```

Требования:

- `timestamptz`;
- UTC;
- PK;
- UNIQUE для защиты от дублей;
- индекс по:
  - `instrument_id`;
  - `ts_event`;
- идемпотентная загрузка;
- `raw_payload` хранить в `jsonb`, если исходное сообщение доступно;
- повторный запуск collector не должен бесконтрольно создавать дубли.

Не выполнять массовые `UPDATE` RAW.

# 12. DDS

На первом этапе можно подготовить DDL без запуска полноценного ETL.

Минимальная будущая таблица:

```text
dds.candle
```

Логический ключ:

```text
instrument_id
timeframe
open_time
```

Не смешивать RAW и DDS.

RAW:

```text
источник / восстановление
```

DDS:

```text
нормализованные данные для аналитики
```

# 13. Market Data Collector

Реализовать:

```text
collectors/bybit_market_data.py
```

Collector должен:

1. запустить NautilusTrader node;
2. подключиться к Bybit;
3. загрузить описание Spot-инструментов;
4. подписаться на данные:
   - `BTCUSDT-SPOT`;
   - `ETHUSDT-SPOT`;
5. получать минимум 1-minute bars;
6. логировать полученные данные;
7. сохранять их в PostgreSQL;
8. корректно завершаться по `Ctrl+C`.

Желательно дополнительно подготовить возможность получать:

```text
QuoteTick
TradeTick
```

но это не является блокирующим требованием первого этапа.
